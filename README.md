# devops-8byte — AWS Infrastructure, CI/CD, and Monitoring

A small Flask task-list API, deployed to AWS with Terraform, GitHub Actions
CI/CD, and CloudWatch monitoring — built for the 8Byte DevOps assignment.
Every design decision below optimizes for one thing above all else: **staying
at effectively zero real-world cost** while still meeting every requirement
in the assignment brief.

## Architecture

```
                            Internet
                               │
                        ┌──────▼──────┐
                        │     ALB     │  (public subnets, 2 AZs)
                        └──────┬──────┘
                               │ :8080
                  ┌────────────▼────────────┐
                  │   EC2 (t3.micro)        │  public subnet
                  │   Docker: Flask app     │  SSM-managed, no SSH
                  │   + CloudWatch Agent    │
                  └────────────┬────────────┘
                               │ :5432
                  ┌────────────▼────────────┐
                  │   RDS PostgreSQL         │  private subnets, 2 AZs
                  │   (db.t3.micro)          │  no public access
                  └──────────────────────────┘
```

**Observability data flow** (separate from the request path above — this
runs alongside it, not in response to a request):

```
EC2 (system logs)   ──▶  CloudWatch Logs  (/devops-8byte/dev/system)
EC2 (app logs)       ──▶  CloudWatch Logs  (/devops-8byte/dev/app)
ALB (access logs)   ──▶  S3

EC2 + RDS + ALB metrics ──▶ CloudWatch Alarms ──▶ SNS topic ──▶ email
```

- **VPC**: 1 VPC, 2 public subnets (ALB + EC2) and 2 private subnets (RDS
  only), across 2 availability zones for basic HA. No NAT Gateway — RDS
  never needs outbound internet, so there's nothing to save cost on there.
- **Compute**: a single EC2 t3.micro instance, managed exclusively through
  AWS Systems Manager (SSM) Session Manager — no SSH key pairs, no open
  inbound ports on the instance's security group at all.
- **Database**: RDS PostgreSQL (db.t3.micro), private subnets only,
  credentials generated by Terraform and stored in SSM Parameter Store
  (`SecureString`), never in plaintext state output or version control.
- **Load balancing**: an Application Load Balancer in front of the EC2
  instance. This is the **only** resource in the entire project without a
  free tier — see the cost section below for how that's managed.

## Repository layout

```

environments/dev/     # all "real" infrastructure (VPC, EC2, RDS, ALB,
                       # monitoring, IAM/OIDC for GitHub Actions)
```

## Setup / how to run this yourself

**Prerequisites**: an AWS account, AWS CLI configured, Terraform ≥ 1.11
(for native S3 state locking), and the [Session Manager plugin][ssm-plugin]
for the AWS CLI.

[ssm-plugin]: https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html

```bash
# 1. Bootstrap remote state (once, ever)
cd bootstrap
terraform init && terraform apply

# 2. Configure environments/dev/backend.tf with the bucket name from
#    step 1's output (this file is committed with a real bucket name —
#    see the note on backend.tf in the table below for why that's fine
#    here but wouldn't be in a multi-account setup).

# 3. Copy and fill in real variables
cd ../environments/dev
cp terraform.tfvars.example terraform.tfvars
# edit terraform.tfvars: set github_repo and a real alert_email

# 4. Provision everything
terraform init
terraform apply

# 5. Get the live URL
terraform output alb_dns_name
curl $(terraform output -raw alb_dns_name)/health
```

**CI/CD**: push to a branch, open a PR touching anything under `app/` —
`ci.yml` runs lint + tests + a dependency CVE scan automatically. Merging
to `main` triggers `cd.yml`: build → Trivy image scan → push to GHCR →
auto-deploy to staging → **pause for manual approval** → deploy to
production. Both staging and production currently point at the same EC2
instance (a deliberate simplification for a demo/assignment environment —
see `NEXT_STEPS.md` for the real fix).

`cd.yml` also has a `workflow_dispatch` trigger, so a deploy can be forced
manually from the Actions tab without needing a new commit — useful for
re-running a demo or recovering after an out-of-band infrastructure change
(e.g. a `terraform apply` that recreates the EC2 instance, which needs a
fresh app deploy). `ci.yml` deliberately does **not** have one: it exists
specifically to gate pull requests against the code in that PR, so manually
dispatching it outside of a PR context wouldn't test anything meaningful —
there'd be no PR to report the check result back to.

**Access the instance** (no SSH, ever):
```bash
aws ssm start-session --target $(terraform output -raw ec2_instance_id)
```

**Teardown** (stops all billing):
```bash
terraform -chdir=environments/dev destroy
```

## Security considerations

- **No SSH anywhere.** All shell access to the EC2 instance goes through
  SSM Session Manager — no key pairs to generate, rotate, leak, or manage,
  and no port 22 open on any security group.
- **RDS is never publicly reachable.** It lives in private subnets with a
  security group that only accepts traffic from the EC2 instance's
  security group, on port 5432.
- **Secrets never touch version control or plaintext state output.**
  The DB password is generated by Terraform (`random_password`) and stored
  as an SSM `SecureString` parameter; the app reads it at container start
  via an SSM `get-parameter --with-decryption` call baked into the deploy
  script, not as a Terraform output or an environment file in the repo.
- **GitHub Actions authenticates to AWS via OIDC, not long-lived keys.**
  No `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets exist anywhere
  in this repo or its GitHub secrets. The workflow assumes an IAM role
  scoped to this exact repository via a short-lived OIDC token, following
  GitHub's [documented recommended pattern][oidc-docs].
- **Every container image is scanned before it ships.** Trivy scans the
  built image before it's pushed to GHCR, and a separate scan checks
  `requirements.txt` for known-vulnerable Python packages on every PR.
  See `CHALLENGES.md` for how the image-scan policy (fail on fixable
  findings, don't block on upstream-unfixed base-image CVEs) was decided.
- **Production deploys require a human.** The `production` GitHub
  Environment has a required-reviewer protection rule, so `cd.yml` pauses
  and waits for manual approval before touching production — verified
  live, not just configured.
- **Least-privilege IAM.** The EC2 instance's IAM role only grants what
  SSM management and CloudWatch Agent operation actually require; the
  GitHub Actions OIDC role is scoped narrowly rather than using
  `AdministratorAccess`.

[oidc-docs]: https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect

## Cost optimization

This project is designed to run for effectively **under $1 total**, even
across multiple full apply/destroy cycles during development:

| Decision | Why |
|---|---|
| No NAT Gateway | Saves ~$32/month; RDS never needs outbound internet |
| SSM Parameter Store, not Secrets Manager | Secrets Manager is $0.40/secret/month; SSM `SecureString` is free |
| SSM Session Manager, not SSH/bastion | Zero cost either way, but removes a whole class of exposure |
| S3-native state locking (TF ≥ 1.11), not DynamoDB | One fewer resource; same safety guarantee |
| GHCR, not a private registry | Free for public repositories |
| `t3.micro` / `db.t3.micro` everywhere | Free-tier eligible instance sizes |
| Apply → verify → destroy discipline | The ALB is the only non-free resource; kept live only while actively verifying or recording |

## Monitoring & logging

**Dashboards** — two CloudWatch dashboards:
- `devops-8byte-dev-infra` — EC2 CPU, memory, and disk (via the
  CloudWatch Agent), RDS CPU/connections/free storage, and ALB target
  health.
- `devops-8byte-dev-app` — request count, response codes grouped by
  status class (2xx/4xx/5xx), p50/p99 latency, and a live widget showing
  recent app log lines.

**Alarms** — five alarms, all wired to a single SNS topic:
- EC2 CPU above threshold
- RDS free storage below threshold
- RDS CPU above threshold
- ALB 5xx rate above threshold
- ALB unhealthy target count above zero

**Logs** — two CloudWatch log groups, plus S3:
- `/devops-8byte/dev/system` — syslog, shipped by the CloudWatch Agent
- `/devops-8byte/dev/app` — the Flask app's own stdout, shipped via
  Docker's `awslogs` log driver
- ALB access logs — shipped directly to S3, not CloudWatch (this is how
  ALB access logging works natively; there's no CloudWatch Logs option
  for it)

**Notifications** — SNS topic with a single email subscription. See
`CHALLENGES.md` for a couple of real gotchas around SNS's confirmation
flow that are easy to miss (a "Confirmed" badge in the console isn't
sufficient proof notifications actually work).

### Local-only (gitignored)

| Path / pattern | Why it's excluded |
|---|---|
| `environments/dev/terraform.tfvars` | Contains the real `alert_email` and `github_repo` values for this specific deployment — not secret exactly, but environment-specific and not meant to be a shared default. `.tfvars.example` documents the shape without committing real values. |
| `*.tfstate`, `*.tfstate.*` | Terraform state should never be read from a local file in a remote-state setup — this is a safety net in case one gets created locally by accident (e.g. running `terraform init` without the backend configured yet), since a stray local state file could silently diverge from the real S3-backed state. |
| `**/.terraform/*` | Terraform's local working directory (downloaded providers, cached modules) — large, regenerated by `terraform init`, and provider binaries are platform-specific so committing them would break `init` on a different OS/architecture. |
| `.terraformrc`, `terraform.rc` | Local CLI configuration (e.g. provider mirror settings) — machine-specific, not part of the project itself. |
| `.DS_Store` | macOS Finder metadata — pure OS noise, no project relevance on any platform. |
| `crash.log`, `crash.*.log` | Terraform crash logs, generated only when the CLI itself hits an internal error — never something to commit, and would leak local paths/environment details if it ever contained one. |
